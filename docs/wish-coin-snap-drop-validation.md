# 위시 동전 정렬 후 낙하 검증

## 현재 변경

드래그한 하나의 동전 DOM을 유지하며 놓은 좌표에서 300ms 동안 곡선으로 정렬하고, 100ms 대기한 뒤 500ms 동안 수직으로 떨어뜨린다. 정렬·대기까지 원래 크기를 유지하고, 낙하 초반에도 큰 크기를 유지하다가 부드럽게 축소·회전해 투입구 안으로 들어간다. 앞면은 실제 투입구 앞 테두리를 따라 동전을 가린다.

- 동전 PNG는 432×432px이다. `sharp`로 alpha > 128을 측정한 픽셀 범위는 x=86…347, y=78…348이며, 반열린 경계는 (86,78)–(348,349)이다. 144px 렌더에서 보이는 폭은 약 87.33px다.
- 고정 몸통 기준인 웃는 토끼 PNG는 1086×1448px이며 본체와 앞면 가림 레이어 모두 CSS 207×277px로 명시한다. 투입구 앞 테두리를 원본의 (388,634)–(650,665)로 측정했다. 화면상 폭 약 49.94px, 중심 x≈190.92px, 앞 테두리 y≈431.28…437.21px다.
- 보이는 동전 중심이 투입구 중앙에 오도록 정렬 위치를 x≈118.59px, y=150px로 잡는다. 기존 144px 상자의 아래쪽과 귀 사이에는 16px 여백을 유지한다.
- 낙하 첫 20%(100ms)까지 scale=1, 회전=0을 유지한다. 이후 78%(390ms)까지 smoothstep으로 균일 배율 0.50, 평면 회전 7.5°, 얕은 Y축 회전 -12°에 도달한다. 시작과 끝에서 크기·회전의 변화 속도가 0으로 이어진다. 낙하 48%의 배율은 약 0.763으로 이전 0.557보다 크다.
- 최종 회전된 보수적 알파 경계 폭은 약 48.24px이며 투입구 좌우에 각각 약 0.848px 여유가 남는다. 기하상 첫 테두리 접촉은 낙하 약 81.67%(408.35ms)이므로 축소는 접촉 약 18ms 전에 완료된다. 낙하 78%부터 마지막까지 0.1% 간격으로 네 모서리의 좌우 경계를 검사한다.
- 동전의 알파 중심을 변환 원점으로 사용하므로 축소·회전 중 수평 중심이 움직이지 않는다. 불투명도 변화나 이미지 교체는 없다.
- 동일한 토끼 앞면 이미지에 기울어진 polygon clip을 적용한다. 낙하 전에는 가림 레이어가 없으며, 낙하 중 동전 하단부터 가려지고 마지막에는 완전히 숨는다.
- 기존 경계를 포함한 동전 중심 판정, grab offset, 200ms 복귀, 취소·lost capture, 한 포인터 추적, 수락 즉시 잠금, unmount 취소, 모션 감소와 단일 callback을 유지한다.
- 카드/위시 funding 티켓, 금액, 버전, 멱등성 키, pending, 오류 재시도와 완료·오류 경로를 변경하지 않는다.

## 표정 전환의 고정 프레임

`PiggyBankCharacter`는 기본·웃는·하트 표정 및 동전 앞쪽 가림에 같은 `BANK`(left 92, top 310, width 207, height 277)를 사용한다. 완료 화면도 이 렌더러를 사용하므로 기존 top 368 / 중앙 정렬 / 높이 281에서 발생하던 이동과 크기 변화가 사라진다. 원본을 통째로 교체하지 않고 웃는 토끼의 귀·몸통·슬롯을 항상 유지한다.

원본 자산은 수정하지 않았다. alpha > 128의 반열린 범위를 `sharp`로 측정했다.

| 원본      | 해상도    | alpha 경계        | 207×277로 환산한 코 중심 |
| --------- | --------- | ----------------- | ------------------------ |
| 기본      | 620×832   | (0,0)–(619,832)   | (78.794,209.581)         |
| 웃는 표정 | 1086×1448 | (0,1)–(1086,1448) | (79.007,210.237)         |
| 하트      | 1076×1461 | (3,1)–(1076,1461) | (79.741,209.978)         |

부모 세션이 측정한 코 중심을 기준으로 기본 얼굴은 (+0.213,+0.656), 하트 얼굴은 (-0.734,+0.259)px 이동한다. 각 눈과 입 주변만 원본에서 가져오고 radial-gradient 마스크 가장자리 20~30%를 부드럽게 섞는다. 첫 사각형 마스크의 오른쪽 아래 경계가 시각 검토에서 보여 개별 눈·입의 타원 마스크로 교체했다. 얼굴 주변의 원본 재질/음영 차이는 부드럽게 연결되며 귀·슬롯·몸통 외곽은 동일한 원본 픽셀을 사용한다.

E2E는 실제 Next 화면과 서버 액션을 로컬 제어 백엔드에 연결한다. 1280px 마우스와 375px/390px Chromium 터치 에뮬레이션에서 상·하·좌·우·중앙 총 15개 드롭을 검증한다. 기본·수락 후 웃는·성공 후 하트 상태의 실제 `getBoundingClientRect`가 모두 같음을 확인했다. 세 뷰포트에서 얼굴 마스크 밖 네 사각 영역(귀·슬롯·몸통 외곽)의 실제 화면 캡처 SHA-256도 세 표정에서 정확히 같았다. 이 픽셀 비교 캡처에서만 별도로 움직이는 동전을 숨겼으며 사용자용 전체 화면 캡처에는 동전이 그대로 보인다.

기존 동전 DOM 유지, release 좌표, 정렬 대기/낙하 초반 크기, 중간 transform.m11=0.74~0.82, 900ms 전 요청 없음, 지연 응답 중 중복 방지, 요청 본문·버전·멱등성 키, event 완료 경로, 모션 감소 이체 실패/재시도, 터치 취소/잘못 놓기가 모두 통과했다. 가림 레이어는 기존 `FRONT_CLIP`과 웃는 표정 원본을 그대로 사용한다. 동전 기하와 애니메이션 시간, funding 코드는 변경하지 않았다.

## 실제 프레임 확인

각 디렉터리에 `{viewport}-{normal,smile,heart,release,aligned,early-fall,shrinking,before-rim,falling,inside-rim,hidden}.png`를 저장했다.

- 375px: `test-results/wish-coin-snap-drop-Wish-c-50436-all-and-one-delayed-request/`
- 390px: `test-results/wish-coin-snap-drop-Wish-c-3976c-all-and-one-delayed-request/`
- 1280px: `test-results/wish-coin-snap-drop-Wish-c-c17d6-all-and-one-delayed-request/`

구현 담당자는 최종 375px 기본/하트와 1280px 기본 캡처를 직접 열어 첫 사각 경계가 사라지고 얼굴이 국소적으로 부드럽게 합성됨을 확인했다. 부모 세션도 수정된 375px 기본/하트, 1280px 기본, 390px 하트를 독립적으로 열어 사각 경계 제거와 고정 형태·슬롯·프레임을 확인했다. 웃는 상태는 고정 기준 원본 그대로다. DOM 박스 검증과 별도로 위 픽셀 비교를 통해 표정 밖 내부 그림까지 고정됨을 검증했다.

낙하 프레임은 320ms 정렬, 480ms 원래 크기, 640ms 공중 축소, 784ms 테두리 위, 816ms 접촉 직전, 848ms 부분 가림, 880ms 완전 가림 순이다. Playwright clock 시간과 실제 requestAnimationFrame 시작은 한 프레임 차이가 날 수 있다.

## 실행 환경과 범위

초기 focused test에서 CSS 숫자/단위 및 clip-path matcher의 TypeScript 형식을 수정했다. 첫 픽셀 비교는 원위치 동전이 귀 캡처 일부를 가려 실패하여 비교 캡처에서 동전만 숨기도록 수정했다. 제품의 드롭/표정 동작은 변경하지 않았다. 사각 얼굴 패치의 경계를 부모 시각 검토에서 발견해 타원 feather 마스크로 수정한 뒤 E2E와 최종 회귀 검증을 다시 실행했다.

React best-practices 기준으로 정적 표현 데이터를 컴포넌트 밖에 두고 추가 상태/Effect 없이 표정만 파생해 렌더링했다. 모든 장식 이미지는 빈 alt, aria-hidden 및 pointer-events-none을 사용한다.

실물 모바일 기기와 운영 금융 백엔드는 검증하지 않았다. 새 이미지·원본 자산·의존성·API/DB·민감 경로는 변경하지 않았다. 커밋, 기존 PR #180 갱신과 원격 read-back, 52210 미리보기 복구는 부모 세션의 후속 controller 작업이다. 병합이나 배포는 포함하지 않는다.
